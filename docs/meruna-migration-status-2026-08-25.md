# حالة ترحيل مميزات MERUNA إلى clinicos

**التاريخ:** 25 أغسطس 2026
**النطاق:** ترحيل تدريجي داخل فرع `feature/meruna-operations-migration` فقط
**المستودع:** `eng7amedadel7-web/clinicos`

## الخلاصة التنفيذية

أصبحت `clinicos` هي الواجهة الأساسية، مع نقل مجموعة تشغيلية كبيرة من MERUNA إلى الخادم والواجهة الجديدين. لم يتم استبدال تصميم clinicos بواجهة MERUNA القديمة؛ تم الحفاظ على تنسيق MERUNA الحالي مع نقل السلوك والعقود التشغيلية إلى طبقة REST الجديدة، مع إبقاء الاستعلامات مقيدة بالعيادة الحالية والصلاحيات المستخرجة من جلسة المستخدم.

> النتيجة الحالية هي نسخة ترحيل قابلة للبناء والمراجعة، وليست إعلاناً بأن كل تكاملات الإنتاج والقنوات اللحظية وBilling أصبحت مكتملة.

## ما تم نقله وأصبح موجوداً في الفرع

| الوحدة | ما تم نقله | حالة التنفيذ |
|---|---|---|
| Dashboard | ملخص تشغيلي حي من Supabase بدلاً من البطاقات والأرقام الثابتة، مع مؤشرات المواعيد والمحادثات والمتابعات وعدم الحضور وقائمة الانتظار | حي عبر API محمي |
| Waitlist | قائمة حقيقية، hydration لأسماء المرضى والمواعيد، pagination، وعمليات pause/cancel عبر RPC مع فحص ملكية السجل | حي عبر API محمي |
| Follow-ups | قراءة الحالات وتسجيل قرار الموظف والرد والإجراء التالي عبر RPC | حي عبر API محمي |
| No-shows | قراءة وتصنيف وإغلاق الحالات عبر RPC، مع فحص ملكية السجل | حي عبر API محمي |
| Patient 360 | المريض ومواعيده ومحادثاته وحالات المتابعة وعدم الحضور في شاشة واحدة | حي عبر endpoint مقيد بالعيادة |
| Appointment Journey | الأحداث الزمنية للموعد وFollow-up وNo-show في صفحة مستقلة | حي للقراءة |
| Inbox | القنوات الأربع، عدد المحادثات، البحث، اختيار المحادثة، سجل الرسائل، حالة AI/Human، وتحديث صامت كل 30 ثانية مع الحفاظ على الاختيار والمسودة | حي عبر REST؛ Realtime الفعلي مؤجل |
| تعدد الحسابات | اختيار الحساب المسجل داخل كل قناة، مع عرض الاسم والمزوّد والحالة | حي للقراءة والفلترة |
| Inbox operations | ملاحظة داخلية، تأجيل 24 ساعة، وتسجيل نتيجة، مع سجل أحداث مقيد بالمحادثة | حي عبر domain events |
| الرد اليدوي | تجهيز الرد عبر `fn_send_inbox_reply` ثم تمريره إلى webhook الخادم الموجود في `N8N_INBOX_OUTBOUND_WEBHOOK`، دون أسرار أو منطق مزود في العميل | مدمج خادمياً؛ لم يُرسل رد حقيقي أثناء الاختبار |
| AI handoff | تبديل وضع AI/Human عبر `fn_set_conversation_ai_status` الرسمي بدلاً من patch مباشر على الحقول المحمية | حي خادمياً |
| Settings | إدارة الفروع والموظفين والأدوار من بيانات حقيقية، مع تحديث الاسم والدور وفحص ملكية العيادة | حي عبر API محمي |
| الصلاحيات | helper مركزي يقرأ جلسة المستخدم ويستدعي فحص `fn_has_clinic_permission` قبل المسارات الحساسة | مدمج في المسارات المرحّلة |

## التحقق الذي تم تنفيذه

مرّ المستودع بنجاح عبر `pnpm run typecheck` و`pnpm run build:vercel`، بما يشمل الخادم والواجهة والحزم المشتركة و`mockup-sandbox` وscripts. كما تم تشغيل smoke test محلي للخادم، ورفضت المسارات الحساسة الطلبات غير الموثقة باستجابة `401` بدلاً من كشف البيانات.

ظهر تحذير أداء من Vite بسبب حجم حزمة JavaScript الرئيسية الذي تجاوز 500 kB بعد التصغير، ووصل في آخر build إلى نحو 583 kB. هذا تحذير تحسين وليس فشل بناء، والأولوية التالية له هي code-splitting وlazy loading للصفحات الثقيلة.

## ما لم يُعلن اكتماله بعد

لم تتم إضافة اشتراك Supabase Realtime مباشر إلى واجهة clinicos؛ التحديث الحالي صامت عبر polling متحكم به كل 30 ثانية ويتوقف في التبويب المخفي. لذلك يجب عدم وصفه بأنه Realtime كامل قبل إضافة قناة آمنة أو آلية server-mediated مناسبة لبيئة الاستضافة.

لم يتم ترحيل Billing وPaddle وtrial lifecycle إلى clinicos في هذه الدفعة. كما لم يتم تعديل n8n أو credentials أو نقل workflows السبعة. مسار الرد اليدوي أصبح جاهزاً لاستدعاء dispatcher موجود عبر متغيرات بيئية خادمية، لكن لم يتم تنفيذ أي إرسال فعلي لقناة خارجية أثناء الاختبار.

لا تزال بعض الشاشات الثانوية في `operations-pages.tsx` ذات طبيعة prototype أو local state، خصوصاً المهام وبعض صفحات الأتمتة وVoice Agent والخدمات القديمة. الصفحات التشغيلية التي أصبحت ظاهرة في App shell هي Dashboard وWaitlist وFollow-ups وNo-shows وPatient 360 وAppointment Journey وInbox الجديدة.

## الترتيب المقترح للدفعة التالية

الأولوية الأولى هي مراجعة بيانات البيئة في Vercel/Supabase وتشغيل اختبار مستخدم مصادق عليه على العيادة التجريبية، مع اختبار قراءة Inbox والقنوات فقط قبل أي إرسال. بعد ذلك ينبغي إضافة Realtime أو آلية reconciliation مدارة خادمياً، ثم نقل billing وtrial lifecycle، ثم إعادة بناء الشاشات الثانوية التي ما زالت prototype، وأخيراً معالجة code-splitting وتحسين الحزمة الرئيسية.
